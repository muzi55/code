# 03. 필요한 정보를 담는 자료구조

[학습 지도](../README.md) · 이전: [JS 기본기](02-JavaScript-기본기와-함정.md) · 다음: [풀이 패턴](04-정렬-탐색-수학-구간-패턴.md)

자료구조는 기억할 정보를 담는 방식이다. 이름을 먼저 고르기보다 어떤 질문을 빠르게 해야 하는지 먼저 정한다.

## 1. 배열: 위치와 순서가 중요할 때

배열은 인덱스로 값을 읽고 순서대로 순회하는 데 적합하다. JS 배열은 길이가 동적으로 변한다. 참고 PDF의 ‘배열은 크기를 정하면 늘리거나 줄일 수 없음’은 고정 길이 배열을 설명하는 문맥이며 JS Array의 일반적인 사용에 그대로 적용하면 안 된다.

| 작업 | 일반적인 알고리즘 비용 모델 | 의미 |
| --- | --- | --- |
| arr[i] | O(1) | 위치를 이미 알고 읽기 |
| push/pop | 분할상환 O(1) | 끝 추가·삭제 |
| 전체 순회 | O(n) | 원소 n개 확인 |
| includes/indexOf | O(n) | 값의 위치를 모르고 찾기 |
| 앞·중간 삽입/삭제 | O(n) 모델 | 뒤 원소를 옮길 수 있음 |
| slice | 복사한 길이 O(k) | 복사도 실제 작업 |

이는 코딩테스트에서 쓰는 일반적 비용 모델이다. JS 언어 명세가 모든 연산의 정확한 구현과 복잡도를 보장한다는 뜻은 아니다.

### 분할상환이란

push를 할 때 가끔 더 큰 저장 공간을 마련하고 기존 값을 옮길 수 있다. 어떤 한 번은 비싸더라도 긴 연속 작업 전체의 비용을 나누면 한 번당 상수 수준이라는 뜻이다. 매번 배열 전체를 옮긴다고 계산할 필요는 없다.

### 순서를 유지해야 하는가

11번은 점수 조건에 맞는 항목을 원래 순서대로 남긴다. 정렬하면 답이 바뀐다. 21번은 가운데 순위를 묻기 때문에 정렬이 도움이 된다. 같은 배열 입력이어도 목적이 다르다.

연습: `[3,1,3]`에서 ‘중복 없이 최초 순서’는 `[3,1]`, ‘오름차순으로 종류’는 `[1,3]`, ‘연속 중복 제거’는 `[3,1,3]`이다. 출력 차이를 먼저 이해해야 한다.

## 2. Set: 있었는가

Set은 값의 존재를 표현한다. 한 값은 한 번만 저장된다. 존재 여부가 목적일 때 횟수까지 저장할 필요가 없다.

```js
const seen = new Set();
seen.add('A');
seen.add('A');
if (seen.size !== 1 || !seen.has('A')) throw new Error('Set 의미 오류');
seen.delete('A');
if (seen.has('A')) throw new Error('삭제 오류');
```

12번에서 처음 본 기념품을 추가할 때 `seen.has(item)`을 검사한다. `[A,B,A]`에서 두 번째 A는 최초 등장 목록에 다시 들어가지 않는다.

하지만 동명이인 두 명을 세어야 하는 18번에서 Set은 부족하다. ‘A가 있다’와 ‘A가 두 명 있다’는 정보량이 다르다.

### 숫자 같은 객체도 같은 값은 아니다

```js
const points = new Set();
points.add([1, 2]);
points.add([1, 2]);
if (points.size !== 2) throw new Error('배열은 참조로 비교한다');
```

별도로 만든 배열 두 개는 내용이 같아도 다른 객체다. 좌표를 내용 기준으로 중복 제거하려면 제한에 맞는 문자열 키 `'1,2'` 같은 표현을 설계해야 한다. 현재 문제들의 Set 키는 숫자·문자열이라 이 고민이 없다.

## 3. Map: 값마다 정보가 필요할 때

Map의 키는 질문 대상, 값은 기억할 정보다.

| 문제 | 키 | 저장할 값 |
| --- | --- | --- |
| 13 최빈 메뉴 | 메뉴 번호 | 등장 횟수 |
| 16 이전 문자 거리 | 문자 | 마지막 인덱스 |
| 18 미탑승객 | 이름 | 남은 인원 |
| 50 버튼 비용 | 문자 | 최소 누름 수 |

네 문제 모두 Map을 쓰지만 저장하는 정보와 갱신 규칙은 다르다. “Map 템플릿” 하나를 외워 붙이기보다 key/value의 뜻을 먼저 쓴다.

```js
const counts = new Map();
for (const name of ['a', 'b', 'a']) {
  counts.set(name, (counts.get(name) ?? 0) + 1);
}
if (counts.get('a') !== 2 || counts.get('b') !== 1) throw new Error('빈도 오류');
```

### 조회와 갱신의 순서

16번은 이전 위치를 읽고 거리를 계산한 **후** 현재 위치로 갱신한다. 19번은 짝을 찾은 **후** 현재 값을 seen에 추가한다.

반면 13번은 전체 빈도를 집계한 **후** 우승자를 고른다. 정보가 언제 완성되는지가 작업 순서를 결정한다.

### 작은 고정 범위라면 배열

문자가 소문자 26개라면 `counts[ch.charCodeAt(0)-97]`처럼 배열로 횟수를 셀 수 있다. 메뉴 번호가 1~100이라면 길이 101 배열도 가능하다.

값이 0~10^12처럼 넓고 실제 등장 종류는 작다면 거대한 배열보다 Map이 적절하다. 범위 크기와 실제 종류 수를 구분한다.

Map/Set을 해시 구조로 생각할 때 조회·추가 평균 O(1)이라는 통상 모델을 사용한다. 언어 명세가 모든 입력에서 최악 O(1)을 보장하는 것은 아니다. 긴 문자열 키의 처리 비용도 일반적으로 고려해야 한다. 이 문제집은 대부분 키 길이를 20 이하 또는 한 글자로 제한한다.

## 4. 스택: 마지막에 넣은 것을 먼저 꺼낸다

책을 위로 쌓아 위에서 꺼내는 모양을 생각하자. 배열의 push/pop으로 표현한다.

```js
const stack = [];
stack.push(5);
stack.push(3);
if (stack.pop() !== 3) throw new Error('최근 항목부터 꺼내야 한다');
if (stack[stack.length - 1] !== 5) throw new Error('top 오류');
```

스택 top은 마지막 원소다. top을 확인하는 것과 pop으로 제거하는 것은 다르다.

32번에서 결제 `[5,3,0,2]`는 다음 상태를 만든다.

```text
5 추가: [5]
3 추가: [5,3]
0 취소: [5]
2 추가: [5,2]
```

sum만 남겼다면 0을 만났을 때 얼마를 빼야 할지 알 수 없다. 취소 대상 금액을 기억하려고 스택이 필요하다.

### 스택 대신 수 하나로 충분한 경우

33번 괄호는 종류가 하나라 아직 닫히지 않은 개수만 기억하면 된다. 여러 괄호 `()[]{}`가 섞이면 닫는 괄호가 가장 최근 여는 괄호와 같은 종류인지도 확인해야 한다. 이 경우 실제 스택을 사용하는 이유가 생긴다.

‘이 유형은 무조건 스택’보다 ‘답을 결정하는 데 어떤 정보가 필요한가’가 먼저다.

## 5. 큐: 먼저 넣은 것을 먼저 꺼낸다

대기열처럼 앞에서 꺼내고 뒤에 추가한다. 유한한 코딩테스트 입력에서는 배열과 head 인덱스로 간단히 구현할 수 있다.

```js
const queue = ['A', 'B'];
let head = 0;
const first = queue[head++];
queue.push('C');
const rest = [];
while (head < queue.length) rest.push(queue[head++]);
if (first !== 'A' || JSON.stringify(rest) !== '["B","C"]') throw new Error('FIFO 오류');
```

논리적으로 남은 큐는 `queue[head]`부터 끝까지다. 실제 배열 앞부분은 제거하지 않는다.

| 상태 | 의미 |
| --- | --- |
| head < queue.length | 아직 꺼낼 항목이 있음 |
| head === queue.length | 논리적으로 빈 큐 |
| queue.length-head | 남은 항목 수 |

`queue.length>0`만 검사하면 이미 다 읽은 큐를 비어 있지 않다고 착각한다.

### shift를 반복하면 왜 주의해야 하나

배열 맨 앞을 제거하면 나머지 항목들의 위치 조정이 발생할 수 있다. n개 항목을 이런 방식으로 차례로 제거하면 일반 모델에서 n+(n-1)+...만큼의 이동, 즉 O(n²) 비용이 될 수 있다. head 방식은 꺼낼 때 인덱스 하나만 늘린다.

이 방식은 완료 항목을 배열에 남기므로 입력 전체 크기에 비례한 메모리를 사용한다. 10만 개 명령처럼 끝이 있는 처리에는 충분하다. 끝없이 돌아가는 서버 큐라면 원형 버퍼나 주기적인 정리가 별도로 필요하다.

## 6. 자료구조 비교에서 자주 빠지는 질문

“배열과 연결리스트 중 무엇이 빠른가?”만으로는 답할 수 없다. 어떤 작업인지가 중요하다. 배열 인덱스 접근은 빠르다. 연결리스트는 원하는 노드를 이미 알고 있으면 연결 변경이 빠르지만 그 노드를 찾는 데 순회가 필요할 수 있다.

“정렬하면 해결되는가?” 다음에는 “원래 순서를 잃어도 되는가?”를 묻는다.

“Set으로 중복을 지울까?” 다음에는 “중복 횟수가 답에 필요한가?”를 묻는다.

“Map으로 다 저장할까?” 다음에는 “현재 값 하나로 과거를 요약할 수 있는가?”를 묻는다.

## 7. 선택 연습과 답

1. 지금까지 온 사람 수만 필요하다 → 정수 카운터.
2. 같은 이름이 몇 번 나왔는지 필요하다 → Map 또는 제한된 범위의 빈도 배열.
3. 그 번호가 이미 나왔는지 필요하다 → Set.
4. 마지막 편집을 취소한다 → 스택.
5. 가장 먼저 접수한 요청을 처리한다 → 큐.
6. 모든 작업의 최종 합만 필요하다 → 합계 변수.
7. 각 시점의 합도 다시 질문한다 → 누적합 배열.

이유를 함께 말하지 못한 항목은 연결 문제를 손으로 한 번 더 풀자. 배열·Map·Set·스택·큐의 기본만 분명해져도 Lv.1 접근 범위가 크게 넓어진다.
