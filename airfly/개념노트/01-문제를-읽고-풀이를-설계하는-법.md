# 01. 처음 보는 코딩테스트 문제에 접근하는 법

[학습 지도](../README.md) · 다음: [JavaScript 기본기](02-JavaScript-기본기와-함정.md)

이 노트의 목표는 알고리즘 이름을 많이 아는 것이 아니라, 문제에서 필요한 정보를 골라 작은 계산 과정으로 바꾸는 것이다. 처음에는 풀이를 떠올리는 데 시간이 오래 걸리는 것이 자연스럽다. 각 문제에서 아래 여섯 칸을 직접 채우자.

## 1. 문제를 읽으면 무엇부터 적는가

| 질문                     | 적을 내용           | 예시: 가장 많이 주문한 메뉴 |
| ------------------------ | ------------------- | --------------------------- |
| 입력은 무엇인가?         | 자료의 모양과 의미  | 메뉴 번호 배열              |
| 출력은 무엇인가?         | 타입, 개수, 순서    | 번호 하나                   |
| 같은 값이 나와도 되는가? | 중복의 의미         | 같은 메뉴를 여러 번 주문    |
| 동점이면 어떻게 하는가?  | 우선순위            | 번호가 작은 메뉴            |
| 얼마나 큰가?             | n의 최댓값          | 100,000                     |
| 언제 예외적인가?         | 빈 입력, 없음, 경계 | 입력은 비지 않음            |

문제의 배경 이야기를 한 번 읽고 나면 ‘승객’, ‘기념품’, ‘메뉴’를 숫자·문자·배열·상태로 번역한다. 배경을 없애도 계산 규칙이 남아야 한다.

나쁜 요약: “메뉴를 잘 정리해서 답을 찾는다.”

좋은 요약: “각 번호의 등장 횟수를 센 뒤, 횟수가 가장 크고 동률이면 번호가 가장 작은 값을 반환한다.”

좋은 요약에는 구현할 동사가 있다. 센다, 비교한다, 더한다, 제외한다, 순서대로 처리한다. 요약이 불분명하면 코드부터 쓰지 않는다.

## 2. 예시는 정답 확인표가 아니라 손풀이 재료다

13번을 직접 풀어 보자. 입력은 `[3,2,3,2,1]`이다.

| 읽은 값 | 머릿속에 남기는 정보      |
| ------- | ------------------------- |
| 3       | 3번 1회                   |
| 2       | 3번 1회, 2번 1회          |
| 3       | 3번 2회, 2번 1회          |
| 2       | 3번 2회, 2번 2회          |
| 1       | 3번 2회, 2번 2회, 1번 1회 |

손으로 풀 때도 메뉴별 횟수 표가 필요했다. 이 표가 곧 Map이다. ‘해시 문제 같으니 Map’이 아니라 ‘번호별 횟수를 기억해야 하니 Map’으로 연결한다.

처음 보는 문제에서 손풀이가 안 되면 더 작은 입력을 만든다. 다섯 개가 어렵다면 두 개, 세 개만 사용한다. 작은 입력에서도 무엇을 해야 하는지 설명하지 못하면 자료구조를 정할 단계가 아니다.

## 3. 상태: 지나간 정보를 무엇으로 요약할까

상태는 다음 원소를 처리하기 위해 기억해 둘 정보다. 모든 과거를 저장할 필요는 없다.

| 문제의 요구             | 필요한 상태        | 버려도 되는 정보          |
| ----------------------- | ------------------ | ------------------------- |
| 조건에 맞는 개수        | count              | 지나간 원소 자체          |
| 최초 최댓값 위치        | bestIndex          | 최대보다 작은 과거 값     |
| 같은 문자의 최근 거리   | 문자별 최근 인덱스 | 더 오래된 등장 위치       |
| 직전 결제 취소          | 미취소 결제 스택   | 이미 취소한 결제          |
| 현재까지 최고 연속 길이 | current, best      | 모든 과거 구간 목록       |
| 반복 구간 합            | prefix             | 요청마다 다시 더하는 과정 |

변수 선언 전에 문장으로 써 보자.

```text
count = 지금까지 확인한 사람 중 조건을 만족한 사람 수
last[ch] = 현재 문자보다 앞에서 ch가 마지막으로 나온 인덱스
current = 현재 위치에서 끝나는 연속 1 구간의 길이
best = 지금까지 등장한 모든 연속 1 구간의 최대 길이
```

“count는 개수”보다 “무엇을 어디까지 센 개수인지”가 중요하다. 상태의 뜻이 분명하면 언제 초기화할지도 분명해진다. target 하나의 합계는 target을 바꿀 때 0으로 돌아가야 한다.

## 4. 가장 단순한 정답 풀이부터 만든다

19번에서 두 수의 합이 target인지 확인하려면 모든 두 인덱스를 골라 비교할 수 있다. 이중 반복문은 출발점으로 훌륭하다.

그다음 실제 입력 크기를 대입한다.

| 입력 수 n | 두 인덱스 조합 n(n-1)/2 | 판단                         |
| --------- | ----------------------: | ---------------------------- |
| 10        |                      45 | 직접 다 봐도 작다            |
| 100       |                   4,950 | 충분히 작은 후보 수          |
| 1,000     |                 499,500 | 연산 내용과 시간 제한도 고려 |
| 100,000   |           4,999,950,000 | 반복 검색을 줄일 필요가 큼   |

‘초당 몇 번 가능’ 같은 수치를 절대 법칙으로 외우지 않는다. JS 실행 환경, 문자열 처리, 메모리 할당에 따라 달라진다. 우선 50억 후보처럼 확실히 큰 작업을 배제하는 용도로 사용한다.

단순 풀이가 제한 안에 들어가면 그대로 사용해도 된다. 26번은 n≤60이라 세 인덱스 조합도 34,220개뿐이다. 삼중 반복문이라는 이유만으로 실패라고 판단하지 않는다.

## 5. 개선은 ‘반복해서 하는 일’에서 찾는다

19번의 단순 풀이를 말로 써 보자.

```text
현재 x를 정한다.
다른 원소를 전부 읽으며 x와 합이 target인지 본다.
```

x가 정해지면 필요한 상대는 `target-x` 하나다. 결국 매번 하는 일은 “필요한 숫자가 있는지 찾기”다. 지나간 숫자를 Set에 저장하면 전부 다시 읽을 필요가 없다.

| 반복 낭비                         | 개선 질문                                | 후보            |
| --------------------------------- | ---------------------------------------- | --------------- |
| 같은 값이 있는지 계속 검색        | 존재만 저장하면 되는가?                  | Set             |
| 같은 값의 개수를 계속 셈          | 값별 횟수를 저장할 수 있는가?            | Map/카운팅 배열 |
| 같은 앞부분의 합을 다시 더함      | 앞부분 합을 저장할 수 있는가?            | 누적합          |
| 겹치는 고정 길이 구간을 다시 더함 | 빠지는 것과 들어오는 것만 반영 가능한가? | 슬라이딩 윈도   |
| 정렬된 후보를 전부 검색           | 절반을 배제할 수 있는가?                 | 이분 탐색       |
| 같은 작은 문제를 계속 계산        | 작은 문제의 답을 저장할 수 있는가?       | DP              |

개선 방법 이름은 마지막에 붙인다. 무엇을 재사용하는지 설명할 수 있어야 다른 문제에도 옮길 수 있다.

## 6. 코드보다 먼저 3~5단계의 의사코드

16번 ‘이전 같은 문자까지 거리’를 예로 들면 다음이면 충분하다.

```text
최근 위치 표와 결과 배열을 만든다.
현재 문자에 이전 위치가 있으면 현재 위치-이전 위치를 넣는다.
이전 위치가 없으면 -1을 넣는다.
현재 위치를 최근 위치 표에 저장한다.
```

여기에서 마지막 두 줄의 순서가 핵심이다. 저장을 먼저 하면 자기 자신과의 거리를 계산해 0이 나온다. 자연어 순서에서 오류를 발견하면 JS 문법과 동시에 씨름하지 않아도 된다.

## 7. 왜 맞는지 설명하는 작은 습관

처음에는 엄격한 수학 증명보다 다음 질문 세 개에 답해 보자.

1. 시작할 때 상태의 뜻이 맞는가?
2. 원소 하나를 처리해도 그 뜻이 유지되는가?
3. 전부 처리하면 그 상태가 요구한 답인가?

01번 count는 처음 아무도 확인하지 않았으므로 0이다. 새 사람이 조건에 맞으면 1을 더하고 아니면 그대로 둔다. 끝나면 전체 사람 중 조건을 만족한 수다.

이처럼 반복 도중 계속 참인 설명을 **불변식**이라고 한다. 어렵게 들려도 ‘이 변수는 지금 무엇을 뜻하는가’를 계속 지키는 일이다.

포인터 풀이에서는 한 질문을 더 한다. “이번에 버리는 후보 안에 답이 없다고 설명할 수 있는가?” 29번에서 양끝 합이 작으면 현재 왼쪽 값은 다른 더 작은 오른쪽 값과도 목표를 만들 수 없다. 그래서 왼쪽을 버려도 된다.

## 8. 자료구조를 고르는 질문 순서

```text
값 하나로 과거를 요약할 수 있나? → 합, 개수, 최댓값
원래 순서대로 결과를 모아야 하나? → 배열
봤는지만 필요한가? → Set
값마다 횟수/위치/비용이 필요한가? → Map
최근에 넣은 것을 먼저 꺼내나? → 스택
먼저 넣은 것을 먼저 꺼내나? → 큐
순위나 가까운 값이 필요한가? → 정렬 검토
고정 데이터에 구간 질문이 반복되나? → 누적합 검토
가능한 범위가 정렬/단조로운가? → 이분 탐색 검토
```

단서는 후보를 제시할 뿐 정답을 보장하지 않는다. “최소”라는 단어 하나만 보고 그리디로 결정하면 안 된다. 최소 비용 경로, 최소 동전, 최소 원소는 서로 다른 문제다.

## 9. 같은 표현처럼 보여도 다른 문제

| 요청                                 | 핵심 차이                 | 연결 문제      |
| ------------------------------------ | ------------------------- | -------------- |
| 전체 중복 제거 / 연속 중복 제거      | 과거 전체 / 바로 앞       | 12 / 31        |
| 목표 합 존재 / 모든 서로 다른 합     | boolean / 합 집합         | 19 / 20        |
| 정렬 안 된 두 수 / 정렬된 두 수      | Set / 두 포인터           | 19 / 29        |
| 최소값 전부 삭제 / 최초 한 개 삭제   | 값 기준 / 인덱스 기준     | 30             |
| 주어진 이동 실행 / 갈 경로 탐색      | 시뮬레이션 / DFS·BFS 후보 | 35 / 심화 노트 |
| 같은 쿠폰 종류 / 같은 이름의 사람 수 | Set / Map                 | 14 / 18        |

## 10. 막혔을 때의 실제 행동

0~3분: 입력·출력·조건을 한 문장으로 적고 예시를 손으로 푼다.

3~7분: 가장 단순한 정답 풀이를 적는다. 필요한 변수의 뜻과 반복 횟수를 계산한다.

7~12분: 중복되는 계산을 찾고, 없다면 단순 풀이를 구현한다. 작은 테스트부터 실행한다.

12분에도 방법이 없으면 힌트 1만 연다. 추가로 3분 동안 손풀이를 해 본다. 그래도 막히면 힌트 2를 열고 상태를 직접 그린다.

해설을 보았다면 읽는 것으로 끝내지 않는다. 코드를 닫고 의사코드부터 다시 쓴다. 20~40분 뒤 다른 문제를 푼 다음 돌아와 해설 없이 재구현한다.

시간은 학습용 가이드이지 실패 판정이 아니다. 한 문제에서 명확한 사고 하나를 얻었다면 충분한 진전이다.

## 11. 복습에서 확인할 네 문장

- 이 문제의 핵심 조건은 **\_\_**이다.
- 손으로 풀 때 기억한 정보는 **\_\_**이다.
- 선택한 방법이 가능한 이유는 **\_\_**이다.
- 틀리기 쉬운 입력 **\_\_**에서는 **\_\_**를 조심한다.

‘Map을 쓴다’로 끝내지 말고 ‘메뉴 번호별 횟수가 필요해 Map을 쓴다’까지 적는다. 며칠 뒤 문제의 배경을 잊어도 풀이를 다시 만들 수 있는 설명이 목표다.
