# 06. 테스트로 생각을 확인하고, 틀린 풀이를 고치는 법

[학습 지도](../README.md) · 이전: [심화 연결](05-트리-그래프-재귀-DP-연결노트.md)

## 1. 예시 하나를 통과했다고 끝내지 않는다

예시는 문제의 규칙을 보여 주는 일부 입력이다. 일반적인 입력만 통과하고 경계에서 실패하는 풀이가 많다. 테스트는 임의의 숫자를 더 넣는 작업보다 서로 다른 실패 이유를 겨냥하는 작업이어야 한다.

| 분류 | 질문 | 예 |
| --- | --- | --- |
| 최소 입력 | 처음부터 반복문이 안 돌면? | 빈 배열, 길이 1 |
| 경계 | 정확히 같은 값은 포함하는가? | 나이==기준 |
| 중복 | 같은 값이 여러 개면? | [4,4], target=8 |
| 없음 | 답이 존재하지 않으면? | 검색 결과 -1 |
| 전부 해당 | 모든 값이 통과하면? | 전부 같은 나이 |
| 전부 불해당 | 결과가 비면? | 필터 결과 [] |
| 동률 | 어느 항목을 고르는가? | 최초 최대, 작은 번호 |
| 순서 | 뒤집으면 결과가 변하는가? | 결제 요청 순서 |
| 부호 | 음수나 0이 가능한가? | 음수 윈도 최대 합 |
| 규모 | 최대 크기에서도 가능한가? | 반복 검색의 누적 |

입력 제한에 없는 경우를 무조건 추가하지 않는다. n≥1인 함수에 빈 배열을 넣고 실패했다고 잘못된 풀이로 판정하면 명세를 바꾼 것이다.

## 2. 좋은 테스트는 틀린 풀이를 구별한다

19번의 `[2,7,11],9 → true`만으로는 현재 값을 먼저 Set에 넣는 오류를 찾기 어렵다. `[4],8 → false`를 넣으면 같은 원소를 두 번 쓰는 오류가 드러난다. 이어 `[4,4],8 → true`를 넣으면 같은 값 두 개는 허용해야 함도 확인한다.

40번에서 `[2,-1,3,4],2 → 7`만으로는 best=0 초기화 오류를 못 잡는다. `[-5,-2,-3],2 → -5`가 필요하다.

50번에서 입력 가능한 단어만 테스트하면 없는 문자를 무시하는 오류를 놓친다. 버튼 `['AB']`, 대상 `['AZ']`의 답은 1이 아니라 -1이다. 앞의 A가 가능해도 전체 단어를 완성하지 못하기 때문이다.

테스트 이름에 목적을 적으면 좋다. ‘테스트 3’보다 ‘부분 성공 뒤 없는 문자’가 코드가 틀렸을 때 원인을 알려 준다.

## 3. 로컬 테스트 사용법

프로젝트 루트에서 실행한다. Node.js 18 이상과 이 폴더만 있으면 된다.

```sh
# 문서 속 50개 정답 전부 확인
node airfly/test.cjs

# 19번 문서 속 정답만 확인
node airfly/test.cjs 19

# 19번을 직접 푼 파일 확인
node airfly/test.cjs 19 airfly/practice.cjs

# 정답의 추가 비교 검증과 개념노트 실행 예제 확인
node airfly/verify.cjs
```

내 풀이 파일은 문제에 맞는 인자를 받는 solution 함수와 `module.exports = solution;` 한 줄을 가진다. `practice.cjs`에는 처음부터 정답이 들어 있지 않으므로 처음 실행하면 실패가 정상이다.

문제 MD에는 정답 JS 블록과 JSON 테스트가 있다. 테스트 실행기는 그 블록을 직접 읽는다. 다른 파일에 복제된 정답을 실행하는 방식이 아니므로 문서의 코드와 검증 대상이 같다.

반환값과 JSON의 expected를 깊게 비교한다. 배열 순서와 값의 타입도 비교한다. 21번은 원본 변경 금지까지 확인한다. 각 호출에는 2초 제한을 두어 종료하지 않는 풀이를 발견할 수 있게 했다. 이는 공식 채점 시간 기준이나 성능 보증이 아니다.

### args의 모양 이해하기

```text
solution([1,2,3])       → args: [[1,2,3]]
solution([1,2,3], 4)    → args: [[1,2,3],4]
solution([[1,2],[3,4]]) → args: [[[1,2],[3,4]]]
```

args 바깥 배열은 ‘함수의 인자 목록’이다. 원래 입력이 배열이면 괄호가 하나 더 생긴다.

## 4. 실패하면 어디부터 볼까

1. 기대값을 손으로 다시 구한다. 내 코드 결과를 보고 기대값을 바꾸지 않는다.
2. 입력을 줄여도 같은 종류의 실패가 나는지 본다.
3. 상태 변수가 처음 틀어지는 위치를 찾는다.
4. 원인이 해석·방법·구현 중 어디인지 분류한다.
5. 원인 한 개를 수정하고 실패 입력을 다시 실행한다.
6. 관련 경계와 기존 테스트도 실행한다.

문법을 무작위로 바꾸거나 조건에 예외 입력을 하나씩 추가하는 방식은 원인을 숨길 수 있다.

### 디버깅 표 예시: 이전 문자 거리

잘못된 코드가 먼저 last를 현재 위치로 갱신하고 거리를 구했다고 하자.

| 현재 i | 문자 | 갱신 전 last | 기대 거리 | 잘못된 거리 |
| --- | --- | --- | --- | --- |
| 0 | a | 없음 | -1 | 0 |
| 1 | b | 없음 | -1 | 0 |
| 2 | a | 0 | 2 | 0 |

문제는 뺄셈 공식이 아니라 갱신 시점이다. ‘이전’을 읽어야 하는데 이미 ‘현재’로 덮어썼다. 이 한 원인을 고치면 첫 등장과 재등장이 함께 해결된다.

## 5. 오답을 세 종류로 나누기

### 해석 오류

‘이상’을 ‘초과’로 읽음, 인덱스 대신 값 반환, 원래 순서 대신 정렬, 한 개 제거 대신 전부 제거. 이 경우 코드를 더 공부하기 전에 문제에서 놓친 문장을 표시한다.

### 방법 선택 오류

n=100,000에서 모든 쌍 검사, 중복 횟수가 필요한데 Set 사용, 음수가 있는 가변 길이 구간에 단조성을 가정. 단순 풀이와 제한을 연결하는 연습이 필요하다.

### 구현 오류

인덱스 하나 차이, 잘못된 초기값, 이전 상태를 덮어쓴 뒤 읽기, 빈 결과 reduce 초기값 누락. 작은 손실행 표와 경계 테스트가 효과적이다.

‘코딩을 못한다’는 평가는 다음 행동을 알려 주지 않는다. ‘빈 입력에서 초기값을 정하지 못했다’는 다음 연습을 알려 준다.

## 6. 작은 정답과 비교하는 방법

최적화한 풀이가 의심되면 작은 입력에서 이해하기 쉬운 완전탐색 결과와 비교한다. 빠른 풀이와 동일한 알고리즘을 복사해 기대값을 만들면 같은 오류를 공유할 수 있다.

```js
function brutePair(nums, target) {
  for (let i = 0; i < nums.length; i++) {
    for (let j = i + 1; j < nums.length; j++) {
      if (nums[i] + nums[j] === target) return true;
    }
  }
  return false;
}
if (brutePair([4], 8) !== false || brutePair([4, 4], 8) !== true) throw new Error('기준 풀이 오류');
```

이 함수는 큰 입력용 제출 풀이가 아니라, 19번의 Set 풀이를 작은 무작위 입력에서 확인할 기준으로 유용하다.

추가로 결과가 반드시 지켜야 할 성질도 확인할 수 있다. 필터 결과 길이는 원본보다 길 수 없다. 31번 결과에는 이웃한 같은 값이 없다. 46번 전치를 두 번 하면 원래 배열이 된다. 이런 성질은 예시와 다른 각도에서 오류를 찾지만, 그 자체만으로 완전한 정답 증명은 아니다.

## 7. 해설을 본 문제를 내 것으로 만드는 복습

첫 시도에는 힌트를 보는 것을 허용한다. 대신 어느 단계까지 봤는지 기록한다.

| 기록 | 뜻 | 다음 행동 |
| --- | --- | --- |
| 독립 해결 | 방법과 코드 모두 스스로 | 다음 날 혼합 문제로 재확인 |
| 단서 도움 | 힌트 1만 봄 | 단서→방법을 한 문장으로 정리 |
| 상태 도움 | 힌트 2까지 봄 | 상태 변수의 뜻부터 재작성 |
| 해설 도움 | 전체 풀이를 봄 | 코드 닫고 손풀이→의사코드→재구현 |

같은 코드를 바로 따라 치는 것은 이해 확인이 약하다. 다른 문제를 하나 풀고 돌아와 변수의 뜻부터 다시 써 보자. 다음 날에는 문제 제목과 입력만 보고 접근을 말해 본다.

## 9. 다음 단계로 넘어갈 기준

50문제를 모두 읽었다는 사실보다, 새로운 문제에서 입력·출력을 번역하고 단순 풀이를 만든 뒤 그 비용을 설명할 수 있는지가 중요하다.

기초 루프와 배열 문제를 독립적으로 풀고, Set/Map 선택 이유와 순서 규칙을 설명할 수 있다면 스택·큐로 넘어간다. 그다음 정렬과 구간 계산, 이분 탐색을 익힌다. 그래프·힙·DP는 이 기본 사고를 더 큰 상태와 관계에 적용하는 확장이다.

틀린 문제는 포기할 목록이 아니라 다음 연습의 구체적인 재료다. 가장 가치 있는 결과물은 통과 표시와 함께 남긴 ‘내가 놓친 조건 한 문장’이다.
